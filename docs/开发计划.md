# 开发计划与进度

目标：做一个任何 WordPress + TranslatePress 网站都能用的 AI 翻译引擎插件，替代 HHG for TranslatePress 1.0.5，首个使用者是 OKAY EYEWEAR（okayeyewear.com）。

已拍板（2026-11-09）：
- 名称：AI Translator for TranslatePress
- 接口：Gemini 原生 + OpenAI 兼容
- 分发：自己发 zip + GitHub 自动更新

## 第一期：引擎核心 + 设置页 + 本机真实链路测试（✅ 2026-11-09 完成）

- 编号对应协议、整批错位判断、逐条校验、长文拆分、缓存、并发、退避、熔断、额度对接
- Gemini 与 OpenAI 兼容两种接口，功能自动降级
- 设置页、状态与日志页、待复核列表、连接测试、TranslatePress 页面上的状态卡片
- 密钥加密保存、权限与 nonce、无公开接口
- 简体中文界面
- 单元测试 89 条、OKAY 真实数据扫描、Docker 22 个场景
- 详见 `测试报告-第一期.md`

## 第二期：主动补翻队列（✅ 2026-11-09 完成，版本 0.2.0）

- 后台签名访问各页面的译文版本，让 TranslatePress 走正常流程翻译；不直接写 TP 的表
- 页面列表按已发布内容自动生成，加额外页面；编辑后自动重新排队
- 每分钟页数、队列每日字符上限、给访客预留 TP 额度、熔断和服务商问题时整队等待
- 绕开页面缓存，被缓存挡住的访问能识别出来，不会误算完成
- WP-Cron / 后台页推进 / WP-CLI 三种运行方式，「补翻队列」后台页
- 详见 `测试报告-第二期.md`

## 第三期：旧坏译文的体检、修复与回滚（✅ 2026-11-09 完成，版本 0.3.0）

- 体检：扫描 TP 词典表和界面文字表里的状态 1，用同一套校验器 + 跨行检查（同一译文挂在不相干原文上、成段错位的邻近行）；分块执行，不花 AI 费用；WP-Cron / 后台页 / WP-CLI
- 复核：按语言、严重度、问题类型筛选，原文译文并排；可导入外部候选清单（编号 + 原文 + 旧译文三者都对上才算）
- 可选 AI 复核（默认关）：只查勾选或可疑的行，计入每日字符上限
- 修复：先逐行备份到插件自己的表（可下载），只在仍是状态 1 且译文没变时改回状态 0，相关页面进补翻队列重翻；清缓存插件里的页面缓存，CDN 提醒手动清
- 回滚：按批次逐字节恢复；其间被人工改过的行保留不覆盖
- 底线：绝不动状态 2；不清空表、不删行；单次最多 500 行；必须人工勾选；仅管理员 + nonce；无公开接口
- 详见 `测试报告-第三期.md`

## 第四期：首个站点（OKAY）验收（进行中）

情况变化：原维护方已在正式站上线自己的 HHG 修复版并修过一批旧译文、触发过全站。第四期改为**测试站并排对比 + 只读体检**，正式站换不换引擎等报告出来后由 Alan 决定，另出上线方案。

- ✅ 0.4.0 本机准备（2026-11-10）：已验收清单（原维护方修好的行永不被修复）、引擎保护（TP 选的不是本引擎时队列不跑、修复拒绝）、HHG 仍在用时的醒目提示、与正式站同款模型档位（Gemini 3.5 Flash、LOW）的请求核对、阿语「包括 / 保证」误判用例
- ✅ 0.5.0 分批自动修复（2026-11-10，Alan 批准方案）：默认关闭；一次一种语言一批（默认 200，最多 500），备份 → 改回 → 只访问这些页面重翻 → 体检规则复查 → 合格才下一批；超 5% 仍错/没翻、存了英文、接口出错、页面打不开、换引擎、批次被回滚即自动停；自己的每日字符上限默认 TP 上限一半；每批可回滚。OKAY 只在测试站试。
- 测试站测试改由原维护方执行（任务书在 private/，不进 git）。
- 待做（需要先备份测试站、Alan 登录、原维护方确认分工）：测试站换引擎 → 只读体检 + 导入已验收清单和剩余候选 → 24 页按批次改回重翻并与已验收版本对比 → 整批回滚 → 旧候选小批演练 → 真实主机条件（回环访问、WP-Cron、两层缓存、负载）
- 底线不变：不动正式站，不把测试站覆盖回正式站，不批量自动翻译整站，人工译文永不动
