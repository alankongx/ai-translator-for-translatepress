# AI Translator for TranslatePress：架构与维护说明

> 给接手维护的人（或 AI agent）看。先读这一份，再动代码。

## 1. 这个插件做什么

给 TranslatePress 加一个翻译引擎（引擎代号 `aitp`），后端可以接：

- **Google Gemini 原生接口**（`/v1beta/models/{model}:generateContent`，密钥放 `x-goog-api-key` 请求头）
- **任意 OpenAI 兼容接口**（`/chat/completions`，`Authorization: Bearer`），包括 OpenAI、DeepSeek、智谱、OpenRouter 和各种中转站

最高原则：**宁可不翻，不能翻错**。没把握的文字一律不交给 TranslatePress，让它保持未翻译（前台显示原文），之后的页面访问再重试。

它取代的是 HHG for TranslatePress 1.0.5。OKAY EYEWEAR 用 HHG 时出过三类事故：译文对错位置、英文被存成译文、长文被截短。本插件的每个设计都对着这三类事故。

## 2. 和 TranslatePress 的接口（以 TP 3.3.9 为准）

TranslatePress 渲染页面时找出没有译文的字符串，按 `get_chunk_size()` 分块调用引擎的 `translate_array( $strings, $target, $source )`：

- 传进来的是「键 => 原文」，**键要原样带回**。带回的键 TP 存为状态 1（机器翻译）；**没带回的键 TP 存为状态 0**，下次访问会再送来。
- 所以「失败 = 不返回这个键」。本插件绝不把失败的结果返回给 TP。
- 状态 2（人工翻译）的字符串 TP 根本不会送给引擎，本插件也碰不到。
- TP 有全局时间预算 `$trp_machine_translation_deadline`（默认 10 秒），只在两块之间检查。本插件自己另有每次调用的时间预算（设置里的「每次页面访问的秒数」，并且一定小于 TP 锁超时 − 15 秒）。
- TP 的锁表：字符串翻译保存后会留一个「刚翻过」的锁，锁超时（约 50 秒）内同一字符串不会再送来。测试时连续访问要注意这一点。
- TP 的每日字符上限 `trp_machine_translation_settings['machine_translation_limit']`（默认 100 万）**无论开关都会生效**。本插件在发送前先预占字符数，请求没被处理（网络错误、被跳过）就退回，超时则按已计费处理。

引擎注册用两个过滤器：`trp_machine_translation_engines`（下拉选项）和 `trp_automatic_translation_engines_classes`（类名）。引擎类 `AITP_TP_Engine` 继承 `TRP_Machine_Translator`，只在 TP 已加载时才 require。

## 4. 一次翻译的完整流程（`AITP_Translator::translate`）

1. **跳过**：空字符串、JSON-LD 结构化数据、处于退避期的字符串（反复失败的）。
2. **缓存**：命中且重新校验通过就直接用；缓存里的旧结果校验不过会被删掉（防缓存中毒）。
3. **拆分**：超过 6000 字节的长文按段落/句子拆成几段，每段单独翻译。
4. **分轮发送**：第 1 轮每批最多 40 条 / 2500 token，之后每轮条数减半，最多 3 轮。并行请求数默认 3。每个请求都带 `not_after` 和 `deadline`，时间不够的请求直接跳过、不计费。
5. **整批判断（防对错位置，核心）**：解析成功后，先看整批回答是否可信，任一情况成立就**整批丢弃、一条都不用**，这些字符串进入下一轮、用更小的批次重试：
   - 有编号缺了（模型可能从漏掉的那条开始整体错位）
   - 两条不同原文得到同一段译文（错位后最后一条被重复）
   - 校验不过的条数 ≥ max(2, 20% × 批大小)
   - 编号重复或多出、JSON 读不出、回答被截断——这些在解析阶段就整批作废
   一轮里有 2 个以上可疑回答而且没有一个正常回答，就立即停止本次调用（`stop_reason = misaligned`），不再花钱。可疑回答还会计入熔断器（`bad_output`），连续 3 次熔断器打开。
6. **逐条校验**：整批可信后才逐条校验。硬性问题（长度、数字、链接、HTML、保护词、代码、尺码、未翻译、混入其他文字……）不保存，带提示重试。软性问题（多加的说法、术语表）重试一次，仍有问题就按设置「保存并进待复核列表」或「不保存」。
7. **与原文完全相同**（翻译时）：像人名/地名的短词（如 Taizhou）要求模型确认一次才保存；像标题或问句的英文（有 2 个以上功能词、以 ?/! 结尾、7 个词以上）直接算未翻译。未经确认的相同译文永远不会作为兜底被保存。
8. **组装**：拆分过的长文所有段都成功才拼回，拼回后整体再校验一次。任何一段失败，整条不保存。
9. **记录**：失败的字符串写入 `aitp_failures`（第一次失败下次访问就重试，之后退避 5 分钟、30 分钟、2 小时、12 小时）；系统性原因（限流、密钥、额度、超时、时间用完……）不写退避。每次调用写一条 `call` 日志。

## 5. 补翻队列（第二期）

只靠访客触发翻译时，没人访问的页面永远是英文。补翻队列在后台**一页一页访问页面的译文版本**，让 TranslatePress 走它自己正常的翻译流程；本插件**从不直接写 TranslatePress 的表**，所以错位判断、逐条校验、人工译文保护、每日上限全部照常生效。

**页面从哪来**：`AITP_Queue::source_pages()` 按设置收集已发布内容（首页、页面、文章、产品、分类、产品分类……）加上「额外页面」；`sync()` 把每个页面 × 每种语言写入 `aitp_queue`（唯一键 = sha1(译文地址|语言)），已不存在的页面删掉。编辑文章（`save_post`）或分类（`edited_term`）后对应行自动重新排队。

**一次访问**（`AITP_Queue::visit`）：

1. 用 `url_converter` 得到译文地址，加 `?aitp_nc=随机数` 绕开页面缓存。
2. 请求头 `X-AITP-Warm: 时间.随机数.HMAC`，HMAC = sha256(时间|随机数|规范化的路径含查询, 站点密钥)，站点密钥由 `wp_salt('auth')` 派生。签名 5 分钟内有效，随机数只能用一次（transient `aitp_used_<随机数>`）。
   - **路径先规范化**（`AITP_Queue_Logic::canonical_path`，0.6.1）：签名方和验签方都用同一写法，按 RFC 3986 6.2.2——百分号编码一律大写十六进制；编码过的非保留字符（`A-Z a-z 0-9 - . _ ~`）解码；不允许原样出现的字节（非 ASCII、空格、控制符、`"<>\^\`{|}`、后面不是两位十六进制的 `%`）编码。保留字符的编码（`%2F`、`%3F`、`%25`、`%26`…）原样保留，路径大小写和查询顺序不动，不整体 urldecode。
   - 原因（F03）：WordPress 的 HTTP 库（`WpOrg\Requests\Iri`）发送前会把 `%e3` 改成 `%E3`、`%7e` 改成 `~`、原样的中日阿文字编码；`get_permalink` 给出的是小写编码。0.6.0 按原始写法签名、按收到的写法验签，日语 / 阿语等非 ASCII 网址的签名全部不通过。本机按真实 Requests 库核对了 15 种写法（大小写编码、原样 Unicode、保留字符、空格、`%` 落单、查询串），规范化后两边一致。
3. 服务器端（`maybe_warm`，plugins_loaded 优先级 1）验签通过才：定义 `DONOTCACHEPAGE`、发不缓存头、回应头 `X-AITP-Warm: ok`、把 TP 时间预算提高到「每页秒数」（仍小于锁超时 − 15 秒），并在 shutdown 时把本次统计（调用次数、译出条数、失败条数、停止原因、字符数）写进 transient `aitp_warm_<随机数>`。
   - **带了 `X-AITP-Warm` 但没通过的请求**（格式不对、过期、签名不对、重放；0.6.1 起）**不再是普通访问**：`trp_machine_translator_is_available` → false、`trp_allow_string_saving` → false（任何引擎都不翻、TP 不存）、`DONOTCACHEPAGE`、不缓存头，回应头 `X-AITP-Warm: invalid:<format|expired|signature|replay>`；不加预算、不写报告。`visit()` 把原因读进返回值 `sig`，补翻队列记 note `signature`（按访问失败计次，3 次后标失败）、页面映射记 note `signature`、自动修复立即停（原因 `visit_signature`）。后台显示「内部访问签名不通过」。没带这个头的普通访客不受影响。
4. 不跟随重定向，UA 为 `AITP-Queue/版本`（避开 TP 的爬虫判断）。

**访问后怎么处理**（`AITP_Queue_Logic::decide`）：

| 情况 | 结果 |
|---|---|
| 没调用引擎 | 完成（done） |
| 有新译文，或时间用完（deferred） | 马上再访问；连续 6 次还有新文字 → 部分完成（max_visits） |
| 调用了引擎但一条没译出 | 部分完成（strings_failing），1 小时、3 小时、12 小时后再来，之后每天 |
| 停止原因是服务商问题（限流、密钥、额度、错位、超时……） | 页面保持待处理，**整个队列等待** 5 分钟（密钥/账单/模型/请求无效等 30 分钟） |
| 重定向 | 直接失败（redirect） |
| 页面有响应但没有报告 | 多半是页面缓存挡住了（no_report），重试 3 次后失败 |
| 访问不到 / HTTP 错误 | 重试 3 次后失败 |

**什么时候停**：队列自己的每日字符上限（`queue_cap`）；TranslatePress 当天计数达到上限 × (1 − 访客预留)（`tp_limit`），等到第二天；熔断器打开时等熔断结束；每分钟页数上限。同一时间只有一轮在跑（选项 `aitp_queue_lock`，过期自动接管）。

**怎么运行**：开始后由 WP-Cron 每分钟一次（`aitp_queue_tick`，计划 `aitp_minute`，每次最多跑 20–55 秒）；站点关了 WP-Cron 时，可以保持「补翻队列」页打开并点「从本页立即推进」（每次 AJAX 推进一页），或者用 WP-CLI：

```bash
wp aitp queue sync                 # 重新生成页面列表
wp aitp queue start | pause | status
wp aitp queue run --minutes=5      # 前台跑 5 分钟（--pages=N 只跑 N 页）
wp aitp queue retry                # 未完成的重新排队
wp aitp queue clear
```

## 5b. 旧译文体检、修复与回滚（第三期）

入口：设置 → AI Translator →「体检与修复」页，或 `wp aitp audit …`。代码：`includes/wp/class-aitp-audit.php`（WordPress 层）+ `includes/core/class-aitp-audit-logic.php`（纯规则）。

**体检**（不花 AI 费用）：逐张扫描 TP 的词典表 `trp_dictionary_{默认}_{语言}` 和界面文字表 `trp_gettext_{语言}`（界面文字的原文取 `trp_gettext_original_strings`），**只看状态 1**。每张表先做跨行检查（同一译文挂在多条不相干原文上 → 可疑），再按 1000 行一块逐行检查，最后做邻近检查。

| 严重度 | 含义 | 来源 |
|---|---|---|
| 错误 error | 基本可以确定是坏的 | 空译文、结构化数据（JSON-LD）坏掉、校验器硬性问题（截短、缺句、数字/链接/占位符/保护词丢失、原样英文、英文残留……）、AI 复核判定不对应 |
| 可疑 suspect | 规则证明不了，需要人看或 AI 复核 | 同一译文多条原文、成段错位的邻近行（`near_misaligned`）、多词原文与译文完全相同 |
| 待看 review | 校验器的软性提示 | 多出宣传说法、术语表等 |

- 成段错位：同一张表里，错误行（截短、缺句、数字不符等「像错位」的问题）之间相隔 ≤ 5 行、至少 2 条，就把这一段前后各 2 行都标为可疑——短字符串错位后单看往往过得了校验。
- 结构化数据：原文和译文都能解析成 JSON（含 WordPress 把引号转成 `&#8220;` 的情况）时，比对键、`@type` 等形状；形状变了是错误。
- 每条发现记原文和译文的 sha1；重新体检时如果行变了会更新，扫描结束后删掉旧扫描里不再出现的未处理发现。

**原文本来就是目标语言**（0.6.2，体检）：只查出「未翻译」、译文和原文完全相同，而且别的语言的词典表里都没有这条原文（TranslatePress 会把各语言自己的语言切换器文字当成该语言的原文，如 `Sprachauswahl der Website`），改记为「待看意思」`identical_native`，不算错误、自动修复不会挑。英文原文在其他语言表里都有，仍算错误。

**候选清单导入**：JSON 或 CSV，列名 `language/lang/locale`、`id/row_id`、`original/source`、`old/translated/translation`、可选 `table`（gettext）。**编号、原文、旧译文三者都和当前行一致、且仍是状态 1**才加入；人工译文、已变、找不到、已是未翻译的分别计数拒收。

**可选 AI 复核**（设置里打开，默认关）：只发勾选或筛出的行（每次最多 500 条，60 条一组），与翻译共用接口、熔断器、TP 每日字符计数。回答 `mismatch` → 升为错误（`ai_mismatch`）；`match` 只记录，不自动关闭。

**修复**（每次最多 500 行，必须人工勾选或按筛选确认）：
0. （0.6.2）`ignore_user_abort(true)`，主机允许时 `set_time_limit(300)`。第一行改动之前先写批次记录（选项 `aitp_repair_batches`，`state = running`）；全部做完再写成 `state = done`。请求中途被杀、超时、浏览器断开，批次记录也已经在，备份行在 `aitp_repair` 表里。
1. 先把整行（原文、译文、状态）写进 `aitp_repair`，同一次修复是一个批次，可下载 JSON。
2. `UPDATE … SET translated = NULL（词典）/ ''（界面文字）, status = 0 WHERE id = ? AND status = 1 AND BINARY translated = BINARY 旧译文`——行在体检后被改过、变成人工译文、或原文变了，都跳过并计数。
3. 清掉这条字符串在 `aitp_failures` 里的退避记录。
4. 找显示这条字符串的**已知页面**（`AITP_Audit::row_pages`，0.6.0）：`trp_original_meta` 里 `post_parent_id` 关联的已发布文章（地址取补翻队列列表，没有就用固定链接换算成该语言地址）∪ 页面映射里显示这一行的页面。**没有已知页面的行不改回**，跳过原因 `no_page`，发现保持 open，编号在返回值 `no_page` 里；只有显式传 `unlinked`（后台勾选框 / `--include-unlinked`）才改回，并把这个语言的全部页面重新排队（`requeue_lang`，旧行为）。界面文字（gettext）没有已知页面。
   **访问哪个页面**（0.6.2，`AITP_Audit_Logic::visit_pages`）：这行在页面映射里出现过，就只从映射过的页面里挑；`post_parent_id` 关联的页面只在这行没出现在任何映射页面上时才用（F05：之前贪心覆盖会挑到只靠旧关联的博客文章）。给了页面名单（后台「只用这些页面」/ `--pages=`，默认语言或译文地址都行，比较时忽略协议、主机、末尾斜杠，路径按 `canonical_path` 规范化），只用名单里的页面；名单里没有它的页面的行跳过（`outside_pages`，发现保持 open）；有名单时不做整语言重排。
   每行只需一个显示它的页面就能重新翻译：用贪心最少覆盖（`AITP_Audit_Logic::cover_pages`，平局时文章自己的页面优先）挑页面，只把这些页面放进补翻队列（`AITP_Queue::requeue_urls`，不在列表里的补一行，备注 `repair`，`sync()` 不会删掉还没访问的这种行），地址存进批次信息 `urls`。
5. 写完批次记录之后，才对显示这些行的全部已知页面调用 `AITP_Cache_Purge::urls()`：LiteSpeed、W3 Total Cache、WP Super Cache、WP Rocket，以及动作 `aitp_purge_urls`。CDN 要手动清。
   - 0.6.2 起：≤ 5 个地址当场清；更多的放进选项 `aitp_purge_list`，WP-Cron（`aitp_purge_tick`）每次 50 个、每轮最多 10 秒清完；打开「体检与修复」页也会推进 3 秒。列表最多 20,000 个，超出的计数（`dropped`）。地址多于 1,000 时后台建议在缓存插件里清全站，并可一键清空列表。
   - LiteSpeed 用 `\LiteSpeed\Purge::cls()->purge_url( $url, false, true )`（第三个参数＝不出后台提示），旧版没有这个类时才用动作 `litespeed_purge_url`。
   - 缓存插件抛出的异常被捕获并记日志（事件 `cache_purge`），不影响修复和列表继续。
   - 原因（F04）：0.6.1 在保存批次记录之前同步清了约 4,552 个地址；LiteSpeed 每个地址都往后台提示选项里追加一条、并把越来越长的清缓存头重写一遍，请求在保存批次记录前中断，留下有备份、没批次记录的 500 行。

**回滚**按批次：原文没变、当前是状态 0 或 1、且和查到时一样，才写回备份的原文本和状态；当前已是人工译文（状态 2）的保留不动；当前已和备份完全一样的直接算已恢复。恢复后发现重新打开；只清显示这些行的页面缓存，**不再把页面重新排队**（恢复的是已有译文，不需要再翻）。
- 0.6.2：只读 `aitp_repair` 里还没处理的行（`restored = ''`），每行处理完立刻标记，所以中途断了再点一次就接着做完；先写批次信息、最后才清缓存（同上，后台分批）。回滚不撤回这一批排进补翻队列的页面。
- **找回批次**（0.6.2，`AITP_Audit::batches`）：除了选项里的批次记录，还从 `aitp_repair` 按批次汇总，没有记录或记录停在 `running` 的批次标 `incomplete`（后台显示「批次记录不完整」，带语言和备份行数），照样能下载备份和回滚。全部行都已处理的视为已回滚。

**已验收清单**（0.4.0）：人工已核过的译文（例如之前另一轮修复改好的行），按「语言 + 编号 + 原文 + 译文」导入到 `aitp_protect`（JSON 或 CSV，译文列名可用 `translated` 或 `new`）。按编号找行；编号指向别的行时（例如从别的库复制来的站），页面文字表再按「完整原文」精确找，只有唯一一行时才用，并单独报数；同一原文有多行的不加入。原文和译文都和当前行完全一致才加入；体检照样列出，但状态是「已验收」，不算待处理；修复一律拒绝（跳过原因 `accepted`）；候选清单导入也不收。行以后被改了，保护自动失效。可整份移除（按清单名）。

**引擎保护**（0.4.0）：TranslatePress 选的不是本插件引擎、或自动翻译关着时，补翻队列等待（`engine_not_selected` / `automatic_off`，5 分钟后再看），修复直接拒绝——否则改回的行会被别的引擎（例如 HHG）重新翻译。

**分批自动修复**（0.5.0，`AITP_Autofix` + 纯规则 `AITP_Autofix_Logic`，默认关闭）：

1. 挑一批（`AITP_Audit::autofix_pick`）：只挑**页面文字**、**错误**档、状态 open、没有 `auto_retried` 标记的发现；一次只挑一种语言（按设置的语言顺序，空 = 全部按字母序）。结构化数据、以及不在任何已知页面上的行（同修复第 4 步）跳过，记为「留给人工」。0.6.0 起启动时不再自动生成补翻队列列表。
2. 调 `AITP_Audit::repair()`（与手工修复同一条路：备份、只改未变动的机器译文、绝不动状态 2、已验收拒绝），批次信息里加 `auto`。
3. 用补翻队列同样的签名内部访问（`AITP_Queue::visit`）只访问这一批的页面（`AITP_Audit::batch_urls`，即修复时选定的 `urls`），速度沿用队列的「每分钟页数」；**不需要、也不会启动补翻队列**。一轮访问完看还有几行没翻：有进展就隔 60 秒再来一轮，最多 3 轮。
4. 判定（`AITP_Audit::batch_check` + `AITP_Autofix_Logic::judge`）：新译文用体检规则重查；仍然错误的记回发现并加 `auto_retried`（不会再被自动挑中）。分母扣掉期间被人改过（状态 2）或已不存在的行。有英文被存成译文（`untranslated` / `english_residue` / `empty`）→ 停（`english_saved`）；仍错 + 仍没翻 > 5% → 停（`too_many_failures`）；否则清这些页面的缓存，下一批。
5. 其他自动停止：开关关了、TP 不再用本引擎或自动翻译关了、没配接口（启动时就拒绝）；熔断器打开（`provider_breaker`）；访问时引擎报 `auth`/`billing`/`rate_limit`/`misaligned`/`timeout`/`network`/`server` 等（`provider_*`）；一批里页面加载失败 3 次（`visit_failed`）；当前批次被回滚（`rolled_back`）；人工停止（`manual`）。停止时当前批次保持原样，可回滚或稍后继续。
6. 额度：自己的每日字符上限（默认 TP 每日上限的一半），同时遵守 TP 每日上限和队列设置里给访客预留的比例；到了就等到第二天（UTC）继续，不算停止。引擎报 `quota` 也一样。
7. 只能在后台（`manage_options` + nonce）或 WP-CLI 开启和启动；没有公开触发入口。运行靠 WP-Cron（`aitp_autofix_tick`，每分钟），也可以在后台页「从本页立即推进」或 `wp aitp autofix run`。

**页面映射**（0.6.0，`AITP_Pagemap`）：

- 起因：TP 只在字符串位于 `trp-post-container`（文章正文）里时写 `post_parent_id`，且同一地址一天只写一次（transient）；首页、集合页这种主题 / 页面构建器拼出来的页面基本没有关联，修复无从得知该访问哪些页面（OKAY 预检：首页、TR90 关联 0 行）。
- 做法：签名内部访问加上 `aitp_map=1`（在签名的路径里，外人加不了）。这次请求里 `trp_machine_translator_is_available` → false（任何引擎都不翻，含别家插件）、`trp_allow_string_saving` → false（TP 不插入新行、不保存）；挂 `trp_translateable_information`，拿到页面的全部 `translateable_strings`，到该语言词典表按**完整原文**精确匹配（SQL `IN` 后再在 PHP 里逐字节比对），结果随签名访问的报告带回。
- 存储：`aitp_pagemap`（每个地址 × 语言一行：地址、默认语言地址、对象类型/编号、HTTP、页面文字数、找到行数、没有对应行的文字数、时间）+ `aitp_pagestr`（页面 ↔ 行）。访问失败保留上次结果。
- 运行：后台填地址（默认语言，每行一个）或留空用补翻队列列表 × 选的语言；每 5 秒一页，一次最多 3000 个；WP-Cron `aitp_map_tick` / 后台「从本页立即推进」/ `wp aitp map run`。不花 AI 字符。
- 统计：每页显示 TP 关联行数（及其中在页面上的）、找到行数（机器 / 人工 / 未翻译）、没有对应行的文字数；找到 0 行 = 「未覆盖」。
- 导出：选中页面（或全部）上显示的**状态 1** 行，格式即候选清单导入格式（`language/table/id/original/old`，另附 `pages`）。TP 关联了但页面已不显示的行不导出（访问页面也不会重翻它们）。
- 已知副作用：TP 自己写 `post_parent_id` 的那一步仍会照常执行（每地址每天一次）；界面文字（gettext）首次出现时 TP 仍可能插入行（与机器翻译、`trp_allow_string_saving` 无关）。词典表、原文表不变（e2e 已核对）。

**测试记录**（0.6.0，`AITP_Journal`，默认关闭）：

- 打开时记下每张 TP 词典 / 界面文字表当时的最大编号。打开期间引擎每次交给 TP 译文（`AITP_TP_Engine::translate_array` 返回前），按语言 + 完整原文查到对应行，把**行号、之前的 translated（区分 NULL 和空串）、之前的 status、我们的译文**写进 `aitp_journal`；查不到行的（TP 接着会插入新行）记 `row_id = 0`。人工译文（状态 2）不记。记录出错只写日志，不影响翻译。
- 撤销：从新到旧逐条，只有当前仍是状态 1、且译文等于我们的译文（或 `trp_sanitize_string` 之后的样子）才恢复成之前的 translated 和 status；被改过 / 人工 / 已不存在 / TP 根本没存都跳过并计数。顺序上先回滚修复批次，再撤销。
- 新增行（编号大于开始时最大编号）只统计、可下载，**绝不删除**；整库恢复由站长决定。

**底线**：绝不动状态 2；不清空表、不删 TP 的行；没有公开接口，所有动作要 `manage_options` + nonce；体检本身不改 TP 的任何数据。

## 8. 密钥安全

- 加密：有 libsodium 用 secretbox（前缀 `sb1:`），否则 AES-256-GCM（`gcm1:`）；密钥由 wp-config.php 里的 AUTH_KEY、SECURE_AUTH_KEY、AUTH_SALT、SECURE_AUTH_SALT 派生。**换了这些盐，已存的密钥就读不出来**，后台会提示重新填写。
- 密钥只出现在服务器发出的请求头里。日志、错误信息都先经过 `redact()` 去掉密钥。
- 请求不跟随重定向，保留 TLS 校验；自定义接口地址必须是 https，不能带用户名、密码、查询参数。
- 所有后台操作都检查 `manage_options` 和 nonce；没有任何公开接口。补翻队列的内部访问靠服务器端签名，外人伪造、过期、换路径、重放都只会得到一次不翻译、不保存的页面访问（0.6.1 起；之前是普通访问）。

## 9. 发布与更新

- 主文件头里的 `Update URI: https://github.com/alankongx/ai-translator-for-translatepress` 让 WordPress 走 `update_plugins_github.com` 过滤器，`AITP_Updater` 读 GitHub 最新 release。
- release 的标签必须是版本号（`v0.2.0` 或 `0.2.0`），并且附件名必须是 `ai-translator-for-translatepress.zip`。
- **仓库必须是公开的**，否则站点无法匿名读取 release，自动更新不会出现（手动上传 zip 不受影响）。
- 打包：`dev/build-zip.sh`，输出到 `dist/`。发布前务必：改主文件 `Version` 和 `AITP_VERSION`、改 readme.txt 的 `Stable tag` 和更新日志、跑全部测试。

- 测试站管理员密码在 `dev/e2e/.state/admin-pass`（不进 git）。

## 11. 已知限制

- 单条请求（批里只有 1 条）不可能错位，但如果模型持续返回「看似合理的短译文」（例如只翻第一个词），短字符串可能通过校验。整批判断只在一批有 2 条以上时起作用。
- 结构上能查的都查了，但无法判断「语义是否准确」。语义问题靠术语表、保护词、待复核列表和人工抽查。
- 补翻队列靠网站访问自己。主机禁止回环访问、或者有不认查询参数的整页缓存（CDN、服务器缓存）时，页面会以「页面有响应但没有经过处理」失败，需要把 `aitp_nc` 加入缓存例外或用 `aitp_queue_request` 改地址。
- 体检认不出「全是短字符串、且译文都过得了校验」的整段错位：如果附近没有任何一条错误，它们不会被标出来。这种情况要靠导入外部候选清单或对可疑行做 AI 复核。
- AI 复核依赖模型判断，`match` 不会自动关闭发现；`unsure` 留给人看。
- 修复后只有被补翻队列访问到的页面才会重翻；没有页面用到的字符串（例如没被页面渲染的结构化数据）会一直停在「未翻译」，TP 显示原文。
- 测试站跑的是 WordPress 6.8；正式站的 WordPress 和 TranslatePress 版本要在第四期 staging 验收时核对。

## 12. 维护守则

- 改任何校验规则后，必须跑：单元测试 + `okay-scan.php`（不能新增误杀）+ `okay-bad-scan.php`（拦截率不能下降）+ `okay-audit-scan.php`（候选清单检出率不能下降）+ `node scenarios.mjs`。
- 修复只能经由「改回状态 0 → 补翻队列重翻」，不要加直接写新译文的路径；回滚永远不能覆盖状态 2。
- 不要为了「翻得更多」放宽整批判断；漏翻可以下次补，翻错要人工去找。
- 不要把测试台、修复工具、数据库后门放进发布包（`dev/build-zip.sh` 已排除 `dev/`、`tests/`、`docs/`）。
- 不要同时启用 HHG 和本插件的引擎；只能选一个。
