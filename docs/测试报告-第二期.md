|---|---|---|
| 1 | **整站从零开始，完全没有访客** | 54 / 54 页完成，2376 / 2376 条全部翻好，错位 0、英文 0；用时 113 秒（测试时放开了速度上限）；队列记的字符数 = TP 计数 = 196764 |
| 2 | 中途断掉、加锁、再续上 | 跑 7 页后停下；锁还有效时第二轮被拒（busy）；锁过期后自动接管，54 / 54 完成，错位 0 |
| 3 | 队列自己的每日上限设为 20000 字符 | 发到 23321 字符后停下等第二天（超出部分不到一页），状态「已达到补翻队列的每日字符上限」 |
| 4 | TP 每日上限 50000、给访客预留 20% | TP 计数到 44415 时停下（≥ 40000 且 < 50000），留下的额度给真实访客 |
| 5 | 服务商拒绝密钥（401） | 只试了 1 页、只发出 1 个请求，整个队列等待 30 分钟；没有页面被误标为完成或失败 |
| 6 | 内部访问的签名 | 正确签名：接受；**同一签名再用一次：拒绝**；伪造密钥、过期、换成别的页面路径：全部拒绝。被拒绝的请求只是一次普通页面访问（HTTP 200），不加时间预算、不写报告 |
| 7 | 队列运行时访客同时浏览（45 次访问） | 共发送 2360 条（词典 2376 条），**没有重复翻译**；错位 0；访客页面最长 1.56 秒 |
| 8 | 模拟一个按查询参数区分的页面缓存插件 | 队列访问全部绕开缓存，54 / 54 完成，缓存里没有存下任何队列访问的页面 |
| 9 | 模拟一个**忽略查询参数**的页面缓存（访客已把法语首页缓存） | 队列拿到的是缓存页面，识别为「页面有响应但没有经过处理（可能是页面缓存）」，**没有误算完成**，稍后重试，3 次后标为失败 |
| 10 | 编辑一个页面 | 该页 6 种语言自动重新排队（6 行），再跑一轮全部重新翻好，错位 0 |

人工译文（状态 2）：队列只是访问页面，由 TranslatePress 决定送什么字符串给引擎，状态 2 的字符串不会被送来；第一期场景 21 已验证这一点，队列没有绕过它的路径。

## 全套回归

加入队列后重新跑了一遍全部 Docker 场景（第一期 22 个 + 队列 10 个）：**32 / 32 通过**，所有场景错位 0。第一期的引擎行为没有变化。

## 这期发现并修好的问题

- 测试工具：`wp aitp queue run --ignore-rate` 在队列设置还没保存过时不生效，补上了对默认值的过滤。插件本身没有发现问题。

## 上线时要注意

- 队列靠网站访问自己。主机禁止回环访问（防火墙、只监听外网地址）时，页面会显示「网站访问不到自己的页面」。
- CDN 或服务器层的整页缓存如果不区分查询参数，队列访问会被缓存挡住（场景 9）。需要把带 `aitp_nc` 的请求设为不缓存，或用过滤器 `aitp_queue_request` 改用内网地址。
- 站点关闭了 WP-Cron 时，要有服务器定时任务调用 wp-cron.php，或用 `wp aitp queue run`，或在「补翻队列」页点「从本页立即推进」。
- 默认每分钟 4 页、队列每天 30 万字符、给访客预留 TP 上限的 20%。OKAY 上线时按 staging 的实际字符量再调。
